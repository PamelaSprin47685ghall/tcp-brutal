# 0.3.2 范围审计：0.2.x 内容 × 0.3.1 现状 × 缺口

审计基线：`master` = `c1ea1b5`（`v0.3.1`）。只读审计；未改代码、未构建、未上真机。

标签：`v0.2.0=cab0d2a`、`v0.2.1=cd1eac8`、`v0.2.2=3d235d7`、`v0.2.3=8c2c25b`、`v0.2.4=1b64df0`、`v0.3.0=425ce04`、`v0.3.1=c1ea1b5`。

## 0. 结论先行

1. **功能面基本没有丢**：0.2.x 的代码修复几乎都在 0.3.1。0.2.4 的 outq 背压以 `a634d2f` 在 0.3.1；0.2.3 的 `hold_enable=1` 仍在；0.2.2 的 sid、target close、RX rebase、crypto 继承都在。
2. **真正的缺口是发布证据链，不是功能**：0.3.1 没有一次 tag-exact、单次、全绿的发布门。1 GiB 是 byte-exact，但脚本因 `up=252/254` 判 FAIL；DKMS 没跑；watchdog 没部署；首连/稳态/1 GiB 是三次部分运行拼起来的；被测树是 `a21f523`，不是 `v0.3.1` tag。
3. **0.3.1 的短块修复有性能代价**：1 GiB 从 0.3.0 的 737.6 s/11.65 Mbit/s 变成 889.2 s/9.66 Mbit/s；far 修复 30,386 次、250 MB，0.3.0 只有 6,949 次（约 57 MB）。miss 从 42,963 降到 21/24，但 wire 从 2.83 GB 升到 3.07 GB。必须同链路 A/B，不能直接当净收益。
4. **0.3.2 应先做“发布完整性”**：watchdog、tag-exact gate、DKMS、up 判据、NACK 延迟判据、join EPROTO；再做 256 性能（直连对照 + perf-256 P0/P1/P2）。多流 v7、SC-LDPC 码率自适应、Adaptive Phase 2 继续 defer，除非明确扩大范围。

## 2. 四个特别确认

### 2.1 0.2.4 的 outq 背压是否已在 0.3.x

**是。** `a634d2f` 在 `v0.3.1` 历史中；0.3.1 代码有：

- `tbt_fec_tx_outq_high()`：per-carrier 160 条/1.3 MiB、session 2048 条/16 MiB、replay 半环。
- 硬上限仍在 `tbt_fec_out_push()`：per-carrier 384 条/3 MiB、session 2304 条/32 MiB。
- 下溢保护在 `tbt_fec_out_free()`。
- 0.3.1 1 GiB：`fec_outq_drop=0`，far `fec_outq_high_wait=23`，`fec_outq_depth=114`。

**但 0.2.4 gate 从未通过**：唯一一次 `--run`（`release-0.2.4-20261108T071938Z`）在 preflight 因 `near_feeder` FAIL 停止。0.2.4 tag 是 `1b64df0`（backport），`5aad74a`（release prep）不含 fix；0.3.1 用的是 master 版 `a634d2f`。结论：**机制已包含，发布门未重验**。

### 2.2 0.2.3 的 hold 默认是否在 0.3.1

**是。** `tbtun/tbt_core.c:51`：`bool tbt_hold_enable = true;`，`module_param_named(hold_enable, ...)`；`tbt_carrier.c:441` 读取。0.3.1 验收使用默认参数，即 hold=on。

风险未变：hold 直接写 `tcp_sock` 的 cwnd/pacing，不是稳定内核 API；`hold_enable=0` 是回退。0.3.1 没有 hold on/off 的现场 A/B。

### 2.3 0.2.x 的 1 GiB/DKMS 发布门是否在 0.3.1 重跑

**1 GiB：重跑了，但不是发布门。**

- 0.3.0：`sclc-verify-20261108T050950Z`，byte-exact，737.6 s/11.65 Mbit/s，PASS（已知 `replay_miss=42,963`）。
- 0.3.1：`sclc-verify-20261108T064508Z`，byte-exact，889.2 s/9.66 Mbit/s；脚本 verdict **FAIL**，只来自 `near up=252`、`far up=254`；无 DKMS、无 watchdog。
- 0.3.1 的 1 GiB 是 `--one-g-only` 在已 join 的 session 上跑；首连/稳态是另外两次部分运行，不是同一次 gate。

**DKMS：没有重跑。** 最后一次 PASS 是 0.2.0 的 `.65` 真机（`dkms-65-20261107T142840Z`，七步，`DKMS_RESULT PASS`）。0.2.3 gate 因 1 GiB audit 失败跳过 DKMS；0.2.4 gate 未过 preflight；0.3.0/0.3.1 没有 DKMS 阶段。

### 2.4 watchdog 是否部署

**当前 near `.82` 没有部署。**

- 0.3.1 验收：`CHECK watchdog_feeder SKIP (no /dev/watchdog0 holder; left untouched)`。
- 0.2.4 gate：`CHECK near_feeder FAIL (no process holds /dev/watchdog0...)`，这是它唯一失败项。
- `.65` 历史上有 feeder（pid 23184 python3），0.2.0 验收时 PASS；但 `.82` 是当前 near，只有安装套件 `review/wan-experiment/arm64/netwatch-82/`（`install-82.sh --arm` 可武装），没有安装/武装证据。
- 约束：`MAGICCLOSE=0`，一旦 open 武装，唯一回滚是重启；44 s 超时；`--selftest` 不 open 设备。

### 2.5 760K 状态

**只是历史微基准，不在 0.3.1。**

## 5. 不建议在 0.3.2 做

- **不要在没有直连对照时调 256 性能常量**。`perf-256` 明确说：链路若只有约 50 Mbit/s，P0/P1 收益为零；先做直连 60 s。
- **不要把多流 v7 + SC-LDPC 码率自适应 + 性能压榨全塞进 0.3.2**。0.3.1 的发布证据链已经碎了；0.3.2 应先做 release integrity，否则版本号只会增加一个不可复现的 tag。
- **不要重跑 0.2.4 gate**。0.2.4 已被 0.3.x 取代；在 0.3.2 gate 中覆盖 outq 即可；文档标记 `v0.2.4` 为 superseded。
- **不要把 `fec_nack_lat_ns` 累计和当延迟**。这是 0.3.1 验收最大的度量错误；继续用会让“600 s 判据”永远通过而掩盖真实尾部。
