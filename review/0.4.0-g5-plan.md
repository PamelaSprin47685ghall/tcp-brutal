## 4. 窗口有效性（60–80 s）

分析单位是一个 60 s 窗口，不是一次 SSH、也不是一个 10 s 采样点。

`valid=1` 同时要求：

- near 快照时间差 `window_s` 在 **60..80 s**（含端点）。真实主机上
  60 s sleep 加前后快照/停止采样要 66–73 s；旧判据 58..65 s 会把它们
  全部判 invalid。
- far `capture_runs submit_bytes` 窗口差 `app>0`。
- near curl 的 `/proc/<pid>/io wchar` 窗口差 `wchar>0`。
- 窗口末 curl 仍存活（`stream_alive=1`）。

`noisy=1` 的窗口保留原始行，但不进主样本：

- 任一端 1 s 采样的 `up_min < 250`（256 − 6 条已知 path-stuck）；
- `c3 lost/replaced/stall_declared`、`c6 holes_unrecoverable`、
  `c3 stream_reset_tcp_failed`、`c9 fec_drop_sid` 任一窗口增量 > 0；
- `|app − wchar| / app > 5%`。

`valid=0` 的典型原因是源提前读完（`window_s < 60`、curl 结束）或快照
开销过大（`window_s > 80`）；不重试，原样留行并在 `note` 说明。

## 5. 中位数与离散度判据

- 主指标只用 `app_mbps`（far `submit_bytes × 8 / far_window_s / 1e6`）。
- 每个版本先取 `valid=1 && noisy=0` 的窗口；`n < 3` 判
  `INSUFFICIENT (n<3)`，不判优劣。
- 中心用中位数，不用均值。离散度同时报：
  `rel_range = (max − min) / median × 100%`，
  `rel_mad = MAD / median × 100%`。
- 对 A→B：`delta = (median_B − median_A) / median_A × 100%`，
  `disp = max(rel_range_A, rel_range_B)`。

| 条件 | 判定 |
|---|---|
| `|delta| < 5%` | **SAME**：无提升，也无可判定退步 |
| `|delta| ≥ 5%` 且 `|delta| > disp` | **BETTER / WORSE** |
| `|delta| ≥ 5%` 但 `|delta| ≤ disp` | **INCONCLUSIVE**：差值在样本跨度内 |

- 产品判定：0.4.0 对 0.3.3 **SAME 或 BETTER → PASS**；
  **WORSE → FAIL**；**INCONCLUSIVE → 加 block 或重跑**，不得写成
  “趋势向好”。0.3.3 G5 对 0.3.2 的 −1.17% SAME 就是按 PASS 处理的先例。
- block drift：同一版本两个 block 的中位数相差超过固定 5%
  （`(max−min)/min`，以较小者为分母）→ `DRIFT`；此时版本间差值不可信，
  先查环境再决定重跑，不要用“反向 block 已抵消”掩盖。
- `wchar` 只作交叉校验；`wire/app`、CPU、RTT、NACK/replay 只作解释，
  不参与提升/退步判定。

## 6. direct before / after

direct 是链路对照，不是产品判据；它回答“A/B 期间链路本身有没有漂”。

- 3 × 60 s 窗口；near 用 curl-loop 连续 GET far `0.0.0.0:5211` 的同一个
  1 GiB 文件，窗口内不断流；`app = wchar`，`wire/app` 应约 1.0。
- 每轮吞吐前后各 100 次串行 HEAD（每次新 TCP），分别给
  connect / TTFB / total 的 p50/p90/p99；`non-200` 必须为 0。
- direct 行同样按 §4 的 60–80 s 与 §5 的中位数/离散度规则分析。
- 对照判定：before 与 after 的 app 中位数按同一 5%/disp 规则比较。
  SAME/INCONCLUSIVE 表示链路漂移没有超出本次样本跨度；WORSE 表示
  A/B 期间链路确实变了，先查环境、重跑 direct，暂不解读 A/B 的版本差。
  0.3.3 G5 的 before 139.1 / after 125.2 Mbit/s（约 −10%，disp 约 11%）
  就是 INCONCLUSIVE，按链路可用接受，不当作产品退步。
- far 到 near 出口 `171.120.34.226` 的临时 `pref 50` 规则当前不存在，
  见 §7 P1；direct 跑完必须删除。

## 7. 前置缺口（按阻塞程度）

### P0 — 0.4.0 flow teardown（硬阻塞）

- 证据：0.4.0 `f8fab7b` 上，1 GiB 流关闭后 far `streams_active` 在
  **> 2 min** 后仍为 1（`g1-r4/SUMMARY.md`）；G3 在 3 min 后启动新流被
  clean refusal（`fault-0.3.3-20261109T031944Z/SUMMARY.md`）。
- 对 G5 的影响：同一 session 的第 2、3 个 60 s 窗口会启动新 curl；若旧
  flow 未释放，far 会拒绝，窗口 `valid=0`。默认 `SETTLE_TMO=60` 不够。
- harness 现状：`wait_stream_clear` 只查 **near** 的
  `streams_active`，且超时后仍“measuring anyway”；拒绝发生在 **far**，
  所以只查 near 会漏。执行前必须补 far 侧检查，并把超时当作该 arm 的
  硬停止，不得继续测。
- 处理顺序：
  1. 先做 teardown 冒烟：fresh reload 0.4.0，跑一个 60 s 窗口，杀 curl，
     每 5 s 读两端 `streams_active`，记录归零秒数。
  2. 若 ≤ 240 s：主计划可用，`SETTLE_TMO` 设为实测值 + 30 s，每个窗口
     前等两端归零。
  3. 若 > 300 s 或永不归零：主计划阻塞。可退到无代码改动的
     `--runs 1 --blocks 6`：12 个 session、每 session 1 窗口，每版本仍
     6 窗口、顺序仍平衡；代价是 12 次 reload/join（约多 40–60 min），
     且 1 行/block 时 block drift 不可用，改用 direct before/after 作
     漂移对照，并在报告中记录这次偏离。
  4. 根本修复（flow teardown）属于 core，不是 G5 脚本的事。

### P1 — far 路由到 near 地址走 WARP（预检硬失败）

- 当前 far `ip route get 192.168.123.85` 返回 `dev WARP table 50000`；
  `perf-ab.sh` 与 `perf-direct.sh` 的 preflight 都要求 `far dev=eth0`，
  会直接 exit 3。
- 临时处理（测后删除）：
  ```sh
  ssh root@45.11.1.62 'ip rule add to 192.168.123.85/32 lookup main pref 50
                        ip rule add to 171.120.34.226/32 lookup main pref 50'
  # 复核
  ssh root@45.11.1.62 'ip route get 192.168.123.85; ip route get 171.120.34.226'
  ```
- 0.3.3 G5 只用过 `to 171.120.34.226` 的 pref 50，G7 已删；本次两个地址
  都加，避免 preflight 与 direct 返回路径各自失败。不要改 `FAR_DEV=WARP`
  绕过检查。

### P2 — far 5210 源未运行

- 当前 far 5210/5211 都无监听；源文件在
  `/root/sclc-verify-1g/accept-1g.bin`（1,073,741,824 B，sha256
  `e926b854…ad7393`）。
- `far-serve.sh` 默认 `RAW_PY=/root/far-raw-serve.py`，该文件不存在；
  实际 sender 在 `/root/sclc-verify/far-raw-serve.py`。启动时显式覆盖：
  ```sh
  ssh root@45.11.1.62 'setsid python3 /root/sclc-verify/far-raw-serve.py \
      --file /root/sclc-verify-1g/accept-1g.bin --bind 127.0.0.1 --port 5210 \
      --log /root/sclc-verify-1g/raw-serve.log \
  ```

- 启动后必须 `HEAD 200` 且 `Content-Length=1073741824`，否则 `perf-ab`
  预检拒绝。测后停掉 5210。

### P3 — 1 GiB 源对 0.4.0 可能偏小

- 1 GiB 在 88 Mbit/s 下约 97 s；一次 curl 从启动到窗口末要
  2 s + 20 s 预热 + 60–80 s 测量，实测窗口 66–73 s 时约 88–95 s，
  valid 上限 80 s 时理论上到 102 s。若 app 接近或超过约 95 Mbit/s，
  源可能在窗口结束前读完，curl 提前退出，该行 `valid=0`。
- 先看 A/B 的 `stream_alive` 与 `window_s`；若出现提前结束，不要把它当
  吞吐，需在 far 另备更大的源（当前未 staging），或接受该版本有效窗口
  减少并在报告中说明。direct 用 curl-loop，不受此限。

### P4 — 现场与工具

- 两端当前都加载 0.4.0 `f8fab7b`（srcversion `FDAE…` / `E5E5…`），
  idle `streams_active=0`，`up=250`（6 条 path-stuck），near pref-100
  存在，netwatch active；far 5210/5211 空闲。A/B 会卸载/重装，属预期。

- 不要停 near 的硬件喂狗者；不要动 far 生产服务。

## 8. 可选：0.3.0 / 0.3.1

- 目的：给 0.4.0 一个同 session 的跨版本锚点。0.3.3 G5 已见
  0.3.0/0.3.1 约 63–65 Mbit/s、0.3.3 约 87.6 Mbit/s（同链路、同日）；
  本次可选跑用来确认这个约 38% 的台阶在当前链路仍在。

  4 版本 × 2 block = 8 个 session、24 个窗口，约 2.5–3 h。
- 注意：4 版本顺序里 0.3.3 与 0.4.0 在 block 1 相邻（第 3、4 臂），
  block 2 也相邻（第 1、2 臂）；这次运行只作参考，**不能替代** §3 的
  两版本主运行作为 G5 判定。
- 若直接复用 0.3.3 G5 的 0.3.0/0.3.1 数字，必须先看 direct before
  是否落在 0.3.3 G5 的 127–142 Mbit/s 区间；不落在区间就重跑。
