# 0.4.x 性能/架构候选分析（只读，基线 0.4.0）

基线：`tbt_uapi.h:30-32` 为 0.4.0；`TBT_FEC_CONV=0x1007`；v7 已有 per-flow FEC，但 SC-LDPC 第二流被拒（`tbt_fec.h:220-247`）。下行固定 binary 1×256/L8/r0.50（`tbt_fec_sclc.h:24-31`、`tbt_fec.c:1863-1909`）；上行 GF16 8×32/L16/r0.25（`benches/adaptive/sclc-0.4.0.sh:389`）。**0.4.x 尚无端到端性能 A/B**（`review/0.4.0-release-checklist.md:44` G5 待跑）；356 MB/s 是 codec 微基准（`host/test_fec_sclc.c:496-536`，1 MiB block、单 share 擦除），不是端到端数字。

## 排序表

| 优先级 | 候选 | 理论提升（≥5% 依据） | 破坏 wire/兼容 | 目标 |
|---|---|---|---|---|
| P0 | 上行 GF16 位切片/SIMD（64-lane 通用位切片 + 4 值平面） | decode 2–5×；p0.4 10.82→22–54 MB/s、5.75→11.5–29 MB/s（host 实测 + i.i.d. 位切片实测） | 否（输出 bit-exact） | 0.4.1 |
| P1 | carriers 默认 64/128（RLNC/grouped 回退路径） | app +21.5%（118.2 vs 97.3 Mbit/s）；CPU/Mbit −11–18%（0.2.1 fix31） | 否（仅默认值） | 0.4.1 |
| P2 | 下行 SC-LDPC 几何参数化 + L16/block512 多码率 | p≤10% wire/app 2.0→1.44（−28%）；p20 −15%；p40 恢复余量（设计表） | 是（CFG profile/映射；旧端显式拒绝） | 0.5.0 |
| P3 | SC carriers 64/128 + 多流 group split | 并发 p99 −30–50%，聚合 0–+10%；解锁当前硬拒绝 | 部分（v7 group bitmap 已有；admission/geometry 变） | 0.5.0（依赖 P2） |
| P4 | 帧级复用多流 | 无独立 ≥5% 证据；公平性/聚合不确定 | 是（block/NACK 语义） | 0.6.0（不先行） |

## 证据边界（先读）

- `host/bench_micro` 链接的是 RLNC/grouped 回退路径（`Makefile:51`，不含 `tbt_fec_sclc.c`/`tbt_sc_ldpc*.c`），**不测生产 `mode=sc-ldpc`**；MICROBENCH 的 1.3–4.4 GB/s 不能当 SC-LDPC 的 CPU 依据。
- 19/5 MB/s 来自源码注释（`tbt_sclc_uplink.c:480-481`）；实测 p=0.40 为 5.69/11.6 MB/s（`review/sc-ldpc-uplink-grouped.md:140-150`），我们重编当前源码为 5.75/10.82 MB/s。p=0 在 c6801ae 后提前返回，不再有“19 MB/s 无擦除”上限。
- 端到端判据以 0.4.0 G5 的 5%/disp 规则为准（`review/0.4.0-g5-plan.md:53,126-137`）：局部加速必须再乘该函数占端到端 CPU 的比例；没有这个占比时，本文只给局部 codec 结论。

## 1. 上行 GF16 位切片（P0，0.4.1）

- 热点：`tbt_sclc_uplink_decode` 逐码字调用 `gf16_decode`（`tbt_sclc_uplink.c:460-585`）；peeling 在 `tbt_sc_ldpc_gf16.c:622-732`；core solve 每码字重做高斯消元（`:397-620`）；nibble 读写 `:65-78`。
- 本机重编实测（Ryzen 9 7940HS，`host/bench_sclc_uplink.c:39-141`，p=0.40）：7/16 10.82 MB/s，1/4 5.75 MB/s；p=0 因 c6801ae 提前返回为 2.6 TB/s，**19 MB/s 是旧口径，不可再当上限**。
- 映射相关性：data `(j+c)%n`、parity `(j+c)%m`，组合周期 `lcm(n,m)`。生产 1/4 为 24（C=128，同 mask 仅 5–6 个码字），7/16 为 126（C=224，仅 2 个）；**不能假设 64 码字同 mask**。二进制下行 64 码字同 mask 的 12.5×（`review/sc-ldpc-bitslice.md`）只适用于旧下行映射。
- 改造：新增 `gf16_decode_batch64`；复用 `tbt_fec_sclc.c:589-655` 的 wave/act 调度，每变量 4 个 u64 值平面 + 1 个未知 mask；每 check 4 个和平面 + 3-bit 计数器（`cnt_add/sub/one`）；GF16 常系数乘用 4×4 二元矩阵（每输出平面 1–4 个 XOR），`x=syn*inv(h)`；gather/scatter 用 64 nibble→4 plane 的 SWAR transpose（复用 `tbt_fec_sclc.c:96-144` 思路）。core solve 按组合相位分组：1/4 可共享 5–6 路，7/16 仅 2 路；不承诺 16×。
- 加速推导：二进制 i.i.d. 位切片实测 2.4–5.5×（`review/sc-ldpc-bitslice.md` §0.2）；GF16 每 payload bit 的边数为 binary 的 1/4，但每边 4 个值平面，且 GF16 标量已比 binary 标量快 4×，故取 2–5×（保守 2×=+100%，中性 3–4×=+200–300%），core/批尾再打折。p0.4：7/16 10.82→22–54 MB/s，1/4 5.75→11.5–29 MB/s。若 0.5.0 改成全局同 mask 映射，才可能进入 12.5× 相关区间。
- 文件边界：新增 `tbtun/tbt_sc_ldpc_gf16_bs.[ch]`（或同文件 batch 函数）；改 `tbt_sclc_uplink_decode` 分批；`tbt_fec_ops` 签名不变；不动 wire。风险：C=224/128 的批尾、相位打包控制、core 正确性；host 对 5 形状 × p=0.3/0.4/0.5 逐字节对比标量 + ASan 必须全绿。

## 2. 下行多码率（P2，0.5.0）

- 现状：`sclc_new` 只接受 n=m=128、block=256、L=8（`tbt_fec_sclc.c:680-720`）；`tbt_fec_sclc_shape_of` 拒绝其他 split（`tbt_fec.c:1880-1909`）。`tbt_fec_adapt_sclc_profile_of` 已定义 A=256/16、B=512/16（rate40）与 6 档 ladder，controller/estimator/CFG 助手齐备（`tbt_fec_adapt_sclc.c:28-246`）；但 downlink `init_plan` 只给当前点，`wire_of_cfg` 仍要求 1×256/block256/L8。
- 实现面：`P=block*L/2`；`C=n*65536/P`（必须整除）；`seg_gather/scatter` 从 8 plane 泛化到 16/32 plane（`tbt_fec_sclc.c:109-144`）；`sclc_build_graph/encode/decode` 常量与 scratch 参数化；`sclc_new` 接受 `(n,m,block,L,rate)`。
- **最大不确定项是 share↔codeword 映射，不是 codec 常量**：当前 1×256/L8 的“每 share 固定 bit 段”只在 `P/n` 为整数时成立（n=128 时 P=1024/2048/4096 都可）；rate60/70 的 n=151/178 会得到非整数 bit/码字/share。设计文档 §3.3 推荐的 B=64 位平面映射尚未定稿，且会改变擦除相关性/q_s；必须先 host BEC 1e6 校准并重测恢复率，不能把旧 64 码字同 mask 的 356 MB/s 直接外推。
- 兼容：旧 0.4.0 的 CFG 用 `d=0`、`k=rate‰`、`w=block`、L 固定 8；新 profile 必须让旧端**显式拒绝**，不能静默按 L8 解码。`FEC_CFG` 的 reserved 必须为 0（`tbt_fec.c:816`），**不能偷用 reserved**；建议 0.5.0 升 `TBT_FEC_CONV 0x1008`，在这次 wire cut 里正式扩展 codec/L/rate 字段。0.4.1 不做。
- 收益（设计表，未实现）：p≤10% rate0.696 vs 0.50，wire/app 2.0→1.438（−28%），wire-bound 时 app +28%；p20 −15%；p30 持平；p40 用 B/512/L16 恢复 0.999168 vs L8 0.9985，减少 NACK/replay。≥5% 只在 p≤20% 成立，故按 `p_est` 启用，p30 不切。
- 版本：**0.5.0**。它同时是 P3（64/128 carriers、多流 group split）的几何前置；0.4.1 不做。

## 3. carriers 默认/自适应（P1/P3）

- 现状：`max_carriers` 默认 256（`tbt_core.c:34-36`）；生产 SC 脚本硬要求 256（`sclc-0.4.0.sh:133-135,626-630`），因 downlink 1×256、uplink 8×32。
- 证据（RLNC/grouped，可迁移的 carrier 成本）：0.2.1 fix31 32/64/256 app 107.6/118.2/97.3 Mbit/s，直连/2 的 96.0/105.4/86.8%；256 far CPU 146.6%、retx 4.9%、txq 16.8 MB 满；64 最佳（`benches/MICROBENCH.md:359-382`）。核/Mbit：near 256 0.00931 vs 64 0.00765，far 0.01507 vs 0.01345；256 app 仍低 17.7%。fix30 256 57.0 vs 64 95.6，far CPU 155% vs 141%，retx 13.5%。
- 折中：每 carrier 一 TCP socket；256 的 per-packet softirq/socket lookup/cache 成本更高，单核先饱和；五元组限速收益近似线性，直到链路或聚合上限。64/128 是单核甜点；256 只在“per-flow cap×N 必须 > 链路”且 CPU 有余时保留。
- 自适应：候选集 `{64,128,256}`，以每 carrier 的 app/CPU 与 p99 为反馈，≥10% 滞回、只在 session 建连/重连时改；运行时逐 carrier 改会破坏五元组与 FEC 几何，不做。
- A/B：用 `benches/adaptive` 的 `--carriers 32,64,128,256`，同 1 GiB/60 s、同 window/replay、3 repeats、交替顺序；指标 app、wire/app、retx、near/far CPU（softirq）、p99 stall、1/4/16 流公平性、直连基线。判定：64 的 app ≥256×0.95 且 CPU/Mbit ≤256×0.90 即改默认；若 cap×64 < 链路，按 cap 反推最小 carrier 数。
- 版本：RLNC/grouped 0.4.1 可改默认（无 wire）；SC 需先做第 2 项几何参数化，**0.5.0**。

## 4. SC-LDPC 多流（P3/P4）

- 事实：v7 已有 per-flow TX/RX、`fec_groups_used`、OPEN 32 B group bitmap、ALLOC（`tbt_fec_data.c:7166-7332`；`tbt_uapi.h:67-73,168-171`）；但 `tbt_fec_flow_admit_check` 对第二 SC 流直接 `-EOPNOTSUPP`（`tbt_fec.h:220-247`），且 downlink codec 固定 1×256，无法给第二流分 carrier。
- 方案 A group split：每流持有 carrier 子集/group；downlink 2×128 或 4×64，uplink 2×4 groups 或 4×2 groups；复用 OPEN bitmap/ALLOC 与 per-flow replay/NACK；需第 2 项 codec 几何参数化 + 放开 admission + 每流 CFG。无新 header；wire 语义不变（group bitmap 已有）。**推荐，0.5.0。**
- 方案 B frame reuse：单 codec 内按 sid 复用 block；省 carrier 分区、允许流共享全部 256，但破坏 per-flow block/NACK/公平性，需新 multiplex 层；**0.6.0，除非 A 的载波利用率不足。**
- ≥5%：并发场景下 2×128 把 block 从 2 MiB 降到 1 MiB，p99 流完成时间约 −50%；聚合吞吐中性到 +10%（避免单流空闲 carrier）。若无并发流工作负载，它只是功能项，不应以吞吐名义排期。
- 版本：A=0.5.0（依赖 P2）；B=0.6.0。

## 5. 建议顺序

1. **0.4.1**：只收不改 wire 的 P0 上行位切片与 P1 carriers 默认 64/128（仅 RLNC/grouped，先 A/B）。仓库惯例是 wire cut 跟 minor 走、patch 不动 wire（0.2.3/0.3.1 先例；0.4.0 已用 `TBT_CONV 0x0007`/`TBT_FEC_CONV 0x1007` 硬切 0.3.x）。
2. **0.5.0**：先做“SC-LDPC 几何参数化 + 新 share↔codeword 映射”（P2 核心），一次解锁 downlink L16/block512 多码率、64/128 carriers、多流 group split；再做自适应闭环与 admission。它需要一次明确的 wire cut。
3. **0.6.0**：仓库目前不需要；仅当 0.5.0 的 wire cut 已冻结、而 frame reuse 还要第二次不兼容改动时才开。group split 的载波利用率/公平性不足是唯一触发条件。
