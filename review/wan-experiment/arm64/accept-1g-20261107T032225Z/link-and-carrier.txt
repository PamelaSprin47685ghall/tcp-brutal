# Round 5: why the carriers dropped and why 2 Mbit/s is an error

## Path measurements (near -> far, direct eth0, no mihomo)

    ping -c 50 -i 0.2 45.11.1.62, tunnel up (idle):   18% loss, rtt avg 297.0 ms
    ping -c 50 -i 0.2 45.11.1.62, tunnel down:        12% loss, rtt avg 299.8 ms
    ping -c 30 -i 0.2 1.1.1.1:                         6.7% loss, rtt avg 271.5 ms
    iperf3 near->far, 5 s, tunnel down, upload:        5.03 Mbit/s sender / 2.59 Mbit/s receiver, 206 retransmits
    iperf3 far->near (-R), 5 s, tunnel running:        0.397 Mbit/s, 25 retransmits (competing with the tunnel)

So the direct path carries a few Mbit/s and loses 12-18% of packets. 1 GiB in the
1800 s budget needs >= 4.8 Mbit/s sustained.

## Why the carriers dropped (tunnel counters at the end)

| counter | near | far |
|---|---|---|
| `lost` | 6 | 4 |
| `replaced` | 6 | 0 |
| `connect_retry` | 52 | 0 |
| `stall_declared` | **0** | **4** |
| `una_stall_us` | 9,673,267 | 7,670,435 |
| `rtt_mean_us` | 316,084 | 315,363 |
| `rttvar_us` | 1,325,389 | 2,848,336 |
| `rtt_max_us` | 4,874,656 | 653,186 |
| `rto_us` | 500,000 | 500,000 |
| `retx_*` | 0 | 0 |

far's `stall_declared` (4) equals far's `lost` (4): the **far-side carrier stall
timer** declared them dead, not a TCP error. `tbt_car_poll_one()` marks a carrier
lost when `una != nxt`, the window is open, and no ACK progress happens for
`carrier_stall_ms` (the config sets 15000 ms). On this path RTTVAR is 1.3-2.8 s
and RTT max 4.9 s, so one loss episode backs the RTO off 0.5 -> 1 -> 2 -> 4 -> 8
-> 16 s; 15 s is inside that backoff. The comment in tbt_carrier.c says the
threshold must exceed several RTTs plus the feedback cadence -- 15 s does not on
this link.

near's 6 losses have `stall_declared=0`: they are the peer closing the socket
(`sk_state != TCP_ESTABLISHED`, rx read returns 0), i.e. the far side closing the
carrier it just declared dead, plus 2 more on the same path.

## What that did to the stream

Lost carriers drop the shares they were carrying. With no NACK (B-01) one
unrecoverable block is permanent: far `c6 holes_unrecoverable=1` and the 30 s
bounded reset killed the stream, so curl saw `rc=18 end of response with
931135686 bytes missing` at 142,606,138 B -- not the 1800 s max-time.

## FEC correctness: fixed by fix5

near c9 `fec_payload_crc_fail` delta 0; near c10 every field 0; far c10 every
field 0 (`fec_decode_blocks=1`, `fec_decode_recovered=1`). far `rx_errs` moved
by 1. The rounds 1/2/4 corruption is gone; the remaining failures are the
carrier stall threshold and the link capacity.
