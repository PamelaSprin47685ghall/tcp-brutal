# 单 256-share 滑窗 RLNC 主机仿真（无 32 分组）

日期 2026-11-06。数据：`review/single-sim.csv`（60 个点，1.2M 次 trial）。
程序：`review/fec-prototype/sim_single.c`，复用未修改的 `rlnc.c` / `rlnc.h`。

模型是一条 256-share 的滑窗 RLNC：N+M=256，K=N，W=2N，L=W，G=2，P=2M。
没有 32 分组；整个 256-share 窗口是一个码。每个 trial 用生产系数生成器编码、
按 p 独立丢数据包、parity 全到、解码、逐字节比对。

## 0. 结论

1. **单码在 750 Mbit/s 应用下恢复率成立，但只对 d=64。** M=64,N=192,d=64
   在 p=1/2/5/10/20% 实测 0.999950 / 0.999950 / 0.999900 / 0.999800 /
   0.999450，全部 ≥0.999。XOR 5.333 GB/s（1 Gbit/s 应用口径），是 HND0
   单核 7.8–9.1 GB/s 的 59–68%。**验收问题"p≤2% 的单 256（M=64,d=64，
   750 Mbit/s，5.33 GB/s）是否成立"：成立。**
2. **d=32 在 M=64 不成立。** p=1% 只有 0.992850（边缘），p=2% 是 0.985600
   （不可行）。0.999 的阈值在 p≈0.14%（模型），0.99 的阈值在 p≈1.39%
   （实测插值）。d=32 只有在 M=96（p≤10%）或 M=128（p≤20%）才够。
3. **单码的恢复率由第二半窗决定。** L=W=2N 时 G=2：g=0 的窗口是
   [-N,N-1]，只覆盖前一半；g=1 覆盖整窗。后半窗只有 M 条方程，前半窗有
   2M 条。恢复率近似 `P ≈ (1-pq)^N (1-pq²)^N`，`q=(1-d/W)^M`。
   60 个实测点与该式平均偏差 1.7e-4，最大 6.8e-3（M=64,d=32,p=20%），
   在 99% CI 量级内。**这是近似模型，判定用实测。**
4. **设计稿的两条硬约束是充分启发式，不是必要条件。** `M >= Wp` 只在
   M=64,p=20% 的 4 个点违反，其中 3 个仍 ≥0.999；`d >= W²p/M` 有 20 个点
   违反，其中 15 个仍 ≥0.999。真正的计数约束是 `M >= Np`（后半窗），
   真正的密度约束是 `(1-d/W)^M ≲ ε/(Np)`，即约 `M·d/W ≳ ln(Np/ε)`。
   设计稿要求每个丢失包被 Wp 条方程覆盖；实际只需要约 ln(Np/ε) 条，
   p=20% 时是 10.6 条对 76.8 条。
5. **把单码挡在门外的是 XOR，不是恢复率。** 只有 4 个 (M,d) 满足
   XOR ≤9.1：M=64,d=32/64；M=96,d=32；M=128,d=32。其中 d=32 在 M=64
   恢复率不够，所以 750 Mbit/s 的唯一可行点是 M=64,d=64（5.333 GB/s）；
   625 Mbit/s 是 M=96,d=32（4.800）；500 Mbit/s 是 M=128,d=32（8.000）。
   （公式含编+解码的 2 倍预算；纯编码实测只有公式的 0.375，判定偏保守。）
6. **判定分布：14 可行 / 2 边缘 / 44 不可行。** 44 个不可行里 40 个是 XOR
   超限，4 个是恢复率 <0.99（全是 M=64,d=32）。d=128/230 全部因 XOR 不可行，
   与恢复率无关（这些点几乎都是 1.000000）。
7. **grouped 仍是默认的理由是 CPU 余量和故障局部化，不是恢复率。**
   grouped M=4,N=4,d=4 在 500 Mbit/s 下只需 1.000 GB/s 标称 XOR
   （1G 线速下 0.500）；单码 M=64,d=64 在 750 Mbit/s 下要 5.333
   （1G 线速下 4.000）。每 Mbit/s 的 XOR 成本单码是 grouped 的 3.6 倍。
   单码每窗恢复率（0.999450）高于 grouped 的 32 组联合（0.9898，推导），
   但 grouped 的失败只影响 1/32 的流，且可以只修复那一组。
8. **p>20% 没有实测。** 矩阵止于 20%。按模型 M=128,d=32（8.0 GB/s，
   500 Mbit/s）在 20% 以上仍有余量，但若要靠增大 d 买恢复率，XOR 立刻
   超预算（M=96,d=64 是 9.6；M=128,d=64 是 16.0）。所以 p>20% 的单码没有
   实测可行点，应转 grouped/SC-LDPC，或接受 500 Mbit/s + d=32 并补测。
9. **内存不是问题。** 工作区 1.01–2.01 MiB；整窗（data+parity+workspace）
   5.01–6.01 MiB。单码每方向一个窗，约 10–12 MiB，占 955 MiB 的 1–2%。

## 1. 方法

### 1.1 几何与分组支撑

| 项 | 值 |
|---|---|
| N+M | 256 |
| K | N |
| W | 2N |
| L | W |
| G = ceil(L/K) | 2 |
| P = G·M | 2M |
| S（trial） | 64 B |
| S（mem 列） | 8192 B |

`rlnc_encode()` 的组窗口是 `ws = g·K + K - W`。代入 K=N、W=2N：
g=0 → ws=-N，只有 `abs = ws + idx >= 0` 的位置存活，即 `idx >= N`，
覆盖 [0,N-1]；g=1 → ws=0，覆盖 [0,2N-1]。用生产生成器直接数
（M=64,N=192,d=64）：g=0 的 4096 个系数里 2100 个落在 [0,191]；
g=1 的 4096 个全落在 [0,383]。M=128,N=128 同型（4187/8192 与 8192/8192）。
存活系数占比 0.756，约 3/4。

所以：

- 后半窗 [N,2N-1] 只被 g=1 的 M 行覆盖；
- 前半窗 [0,N-1] 被 g=0 和 g=1 的 2M 行覆盖。

这是 L=W 的截断形态。稳态（L>>W）每个包都落在两个完整窗口里，后半窗的
劣势会消失；本文按任务要求只测 L=W，也就是最坏形态。

### 1.2 恢复率近似

把方程按块写成 `[[A,0],[B,C]]`：A 是 2M×a（前半窗未知数），C 是 M×b
（后半窗未知数）。C 满列秩时 rank = rank(A)+b，两半可以分开看。
每行覆盖某个特定列的概率是 d/W（d 个互异位置均匀落在 W 上），于是
`q=(1-d/W)^M` 是一列在后半窗被 M 行全部漏掉的概率，前半窗对应 q²。
iid 丢包下 a,b~Bin(N,p)，得到

```
P(recover) ≈ (1 - p·q)^N · (1 - p·q²)^N
```

该式忽略列之间的秩相关（例如两列支撑完全相同），所以是近似；实测表才是
判定依据。60 点平均 |实测-模型| = 1.7e-4，最大 6.8e-3
（M=64,d=32,p=20%：模型 0.8632，实测 0.8564），仍在 99% CI 0.0064 附近。
其余点最大偏差 1.2e-3。

### 1.3 trial 与统计

每个 trial：

1. 用 splitmix64 填满 L×S 字节；种子是 (M,d,p,trial,tag) 的哈希，可复现。
2. `rlnc_new(N,M,N,2N,64,d,nonce)`，nonce 是 (M,d,p,trial) 的哈希。
   每个 trial 是一个新的码实例，所以测的是"随机码实例 + 随机丢包"的
   联合概率。
3. `rlnc_encode()`；每个数据包以 p 独立丢弃；parity 全到。
4. `rlnc_decode()`；逐字节 `memcmp()` 全部 L 个包。
5. 成功 = 返回 >=0 且字节一致；返回 <0 记 stuck；返回 >=0 但字节不一致记
   corrupt。**60 个点 corrupt 全为 0**，失败全部是 `RLNC_ERR_STUCK`。

S=64 的理由与 hnd0 相同：GF(2) 码的秩只取决于系数矩阵，与载荷长度无关；
S=64 仍能做有意义的逐字节校验，而 1.2M 次 trial 才跑得完。mem 列用
S=8192 的生产包长单独计算，是 `rlnc_memory_bytes(ctx,L)` 的返回值
（主要是 `rhs_buf = P·S` 的拷贝）。

每点 20000 次 trial（验收下限 5000）。99% CI 用 Wilson 半宽；最大半宽
0.006387（M=64,d=32,p=20%），r=1.000000 的点是 0.000166。20000 次
0 失败时，精确单侧 99% 失败率上界是 2.3e-4（r 下界 0.99977）。
判定按点估计，不按 CI 下界；两个"可行"点的下界略低于 0.999，见 §7。

### 1.4 构建与运行

```
nproc = 16
CPU   = AMD Ryzen 9 7940H w/ Radeon 780M Graphics
build = cc -O2 -std=c99 -Wall -Wextra -Werror -D_POSIX_C_SOURCE=200809L \
        -pthread sim_single.c rlnc.c -o sim_single
run   = ./sim_single 20000 > ../single-sim.csv
time  = 5m13s wall / 66m55s user（16 线程，动态队列按 d² 从重到轻）
exit  = 0，corrupt = 0
```

程序也接受 `./sim_single [trials] [start] [count]`，用于标定子集；输出始终
是同一张 CSV 表。

## 4. 硬约束 vs 实测

设计稿 §3.5 给两条硬约束：

1. `M >= W·p`：方程数不少于丢失数。
2. `d >= W²·p/M`：每个丢失包要被足够多的方程覆盖（推导：
   `M·(d/W) >= W·p`）。

这两条在 L=W 几何下都不是必要条件，原因见 §1.1/§1.2。下表按矩阵里首次

读数：

- **M >= Wp**：只有 M=64,p=20% 的 4 个点违反（76.8 > 64），其中 3 个仍
  ≥0.999。原因是计数约束作用在**后半窗**：b~Bin(N,p)，均值 Np = Wp/2。
  p=20% 时均值 38.4，64 行足够。设计稿的 Wp 把两半一起数了，偏保守 2 倍。
- **d >= W²p/M**：20 个点违反，其中 15 个仍 ≥0.999，只有 4 个 <0.99
  （全是 M=64,d=32）。它要求每个丢失包被 Wp 条方程覆盖；实际只需要
  ~ln(Np/ε) 条。p=20% 时是 10.6 对 76.8，差 7 倍。所以它在
  M=64,d=32 上方向对、阈值过高：它说 p=5% 需要 d=115.2，实测 d=64
  已有 0.999900。
- 两条约束都不是"实测恢复率"：判定只能用本表的 recovery，不能用约束
  反推。约束的价值是解释为什么 d=32/M=64 会崩，以及为什么分组能把
  d 拉回 4–8。

## 5. XOR 与 goodput

`xor_gbs = (M/N)·d·q·0.125`，q=2，按 1 Gbit/s **应用**载荷（125 MB/s）
计。若线速是 1 Gbit/s（应用只有 N/256 Gbit/s），实际需求是
`xor_gbs × N/256`；判定规则用前者，偏保守。

| M | N | d | app Mbit/s | XOR GB/s (1G app) | XOR GB/s @1G 线速 | 占 9.1 GB/s |
|---:|---:|---:|---:|---:|---:|---:|
| 64 | 192 | 32 | 750 | 2.667 | 2.000 | 29% |
| 64 | 192 | 64 | 750 | 5.333 | 4.000 | 59% |
| 64 | 192 | 128 | 750 | 10.667 | 8.000 | 117% |
| 64 | 192 | 230 | 750 | 19.167 | 14.375 | 211% |
| 96 | 160 | 32 | 625 | 4.800 | 3.000 | 53% |
| 96 | 160 | 64 | 625 | 9.600 | 6.000 | 105% |
| 96 | 160 | 128 | 625 | 19.200 | 12.000 | 211% |
| 96 | 160 | 230 | 625 | 34.500 | 21.562 | 379% |
| 128 | 128 | 32 | 500 | 8.000 | 4.000 | 88% |
| 128 | 128 | 64 | 500 | 16.000 | 8.000 | 176% |
| 128 | 128 | 128 | 500 | 32.000 | 16.000 | 352% |
| 128 | 128 | 230 | 500 | 57.500 | 28.750 | 632% |

说明：

- 只有 4 个 (M,d) 落在 9.1 GB/s 以内：M=64,d=32（2.667）、
  M=64,d=64（5.333）、M=96,d=32（4.800）、M=128,d=32（8.000）。
- 公式的 `2Md/N` 是**每个数据包**的标称 XOR 项数。按窗口直接数是
  `P·d = 2Md` 项除以 `2N` 个数据包，即 `Md/N`。所以 q=2 不是"两组各算
  一遍"（P=2M 已经含了），而是编+解码的 2 倍预算——`hnd0-sim.md` §8
  也是这个读法。g=0 裁剪再乘 0.75，**纯编码只有公式的 0.375**。
- 解码要重算同一批系数并做消元。本机一次性探针（S=8192，单线程，
  3 次取最好）显示：纯编码的 live XOR 是 28.6–44.0 GB/s，
  live/nominal=0.75；在 d=32/64 的可行点上，p=20% 的解码耗时是编码的
  1.3–1.5 倍；系数生成占编码的 4–33%；编+解码合计约为公式的
  0.85–0.93。所以用 q=2 做判定是合理的保守口径，不是 2.7 倍的高估。
- HND0 的 7.8–9.1 GB/s 是 `review/microbench.md` 的单核实测 XOR 字节
  吞吐，不是本机数字。本机（Ryzen 9 7940H）的 XOR 吞吐高得多，不能用
  本机余量替 HND0 判定。
- d=230 的系数生成是 O(d²) 拒绝采样，但 S=8192 时它仍不是主项：本机探针
  里 M=128,d=230 的 encode 是 12.643 ms，其中 `rlnc_coeffs()` 4.179 ms
  （33%），XOR 仍是主项。S=64 的恢复仿真每 trial 约 16 ms，那是小载荷
  放大了系数占比，不能当作生产编码成本。

## 6. p 阈值

`p(0.999)` 是恢复率跌破 0.999 的丢包率，`p(0.99)` 是跌破 0.99 的丢包率。
"模型"列由 §1.2 的近似式解出；"实测"列由矩阵相邻点线性插值，`<1%`
表示 1% 点已经低于目标，`>20%` 表示 20% 点仍高于目标。

| M | N | d | p(0.999) 模型 | p(0.999) 实测 | p(0.99) 模型 | p(0.99) 实测 |
|---:|---:|---:|---:|---:|---:|---:|
| 64 | 192 | 32 | 0.14% | <1% | 1.37% | 1.39% |
| 64 | 192 | 64 | 60.9% | >20% | >99% | >20% |
| 96 | 160 | 32 | 15.4% | 12.9% | >99% | >20% |
| 96 | 160 | 64 | >99% | >20% | >99% | >20% |
| 128 | 128 | 32 | >99% | >20% | >99% | >20% |
| 128 | 128 | 64 | >99% | >20% | >99% | >20% |

d=128/230 的 6 行全部 `>99% / >20%`，没有阈值意义，略去。

**d=32 在哪里停止可行**：

- M=64：p=1% 已经只有 0.992850，属于"边缘"；p=2% 是 0.985600，不可行。
  0.99 的交叉在 p≈1.39%（实测插值），0.999 的交叉在 p≈0.14%（模型，
  矩阵没有低于 1% 的点）。也就是说 d=32/M=64 在 p≥0.2% 时都达不到
  0.999。
- M=96：p≤10% 可行（0.999200），p=20% 是 0.998500（边缘）。0.999 的
  交叉在 12.9%（实测插值）/ 15.4%（模型）。
- M=128：p≤20% 全部 ≥0.99995，0.999 交叉在 20% 以上。

**d=64 在哪里停止可行**：

- M=64：p=20% 仍有 0.999450，模型把 0.999 交叉放在 60.9%，矩阵内没有
  阈值。**所以 p≤2% 的 M=64,d=64 不仅成立，而且余量很大。**
- M=96/128：恢复率不是问题（都是 1.000000），但 XOR 9.6/16.0 超过
  9.1，属于 CPU 不可行。

**验收问题的直接回答**：p≤2% 的单 256、M=64、d=64、app 750 Mbit/s、
XOR 5.333 GB/s **成立**。p=1% 与 p=2% 的实测都是 0.999950
（各 1 次失败 / 20000，Wilson 99% 半宽 0.000210）。

## 7. 判定

按验收口径逐点判定（`xor_gbs <= 9.1` 且 `recovery >= 0.999` 可行；
`>= 0.99` 边缘；否则不可行）：

| 判定 | 点数 | 点 |
|---|---:|---|
| 可行 | 14 | M=64,d=64 全部 5 个 p；M=96,d=32 的 p≤10%；M=128,d=32 全部 5 个 p |
| 边缘 | 2 | M=64,d=32,p=1%（0.992850）；M=96,d=32,p=20%（0.998500） |
| 不可行 | 44 | 40 个 XOR 超限 + 4 个恢复率 <0.99（M=64,d=32,p≥2%） |

需要注意的边界：

- M=64,d=64,p=20% 的 r=0.999450，Wilson 99% 下界是 0.998992，略低于
  0.999；M=96,d=32,p=10% 的 r=0.999200，下界 0.998659，也略低。
  这两行的"可行"是点估计判定，不是 99% 置信的"≥0.999"。其余 12 个可行点
  的下界都 ≥0.999。
- 可行点里 XOR 最紧的是 M=128,d=32（8.000，占 9.1 的 88%），恢复率
  最松的是 M=64,d=64（p=1/2% 各 1 次失败）。
- d=128/230 的恢复率几乎都是 1.000000（唯一例外 M=64,d=128,p=20% 是
  0.999950），但 XOR 10.667–57.500，全部不可行。**恢复率不是单码的
  瓶颈；XOR 才是。**

## 8. 与 grouped 默认的对比

grouped 的数字来自 `review/hnd0-sim.md`（32×8，M=4,N=4,d=4，p=20%，
每 50000 窗口实测）：每组 0.9997，32 组联合 0.9898（r^32，推导）。
单码用本表 M=64,d=64,p=20% 与 M=128,d=32,p=20%。

| 项 | grouped 32×8 M=4,d=4 | 单码 M=64,d=64 | 单码 M=128,d=32 |
|---|---:|---:|---:|
| app goodput @1G 线速 | 500 Mbit/s | 750 Mbit/s | 500 Mbit/s |
| XOR 标称 @1G app | 1.000 GB/s | 5.333 GB/s | 8.000 GB/s |
| XOR @1G 线速 | 0.500 GB/s | 4.000 GB/s | 4.000 GB/s |
| 每 Mbit/s 的 XOR | 2.0 MB/s/Mbit/s | 7.1 MB/s/Mbit/s | 16.0 MB/s/Mbit/s |
| p=20% 恢复率 | 0.9997 每组 / 0.9898 联合 | 0.999450 每窗 | 0.999950 每窗 |
| 缓冲 | 5–7 MiB（32 组） | 5.0 MiB | 6.0 MiB |
| 失败影响面 | 1/32 的流 | 整条流 | 整条流 |

读数：

- 单码的每窗恢复率高于 grouped 的 32 组联合，但 grouped 的"联合"是
  最坏口径：一组失败只影响 1/32 的 seq，可以只修复那一组；单码失败是
  整窗等待。两者不是同一个可用性度量。
- 单码 750 Mbit/s 的 XOR 是 grouped 500 Mbit/s 的 5.3 倍（每应用字节
  42.7 对 8.0），按每 Mbit/s 折算是 3.6 倍。HND0 单核 7.8–9.1 GB/s
  下，单码 4.0 GB/s（1G 线速口径）占 44–51%，再加解码、TCP 与软中断，
  2 vCPU 的余量很薄；grouped 0.5 GB/s 只占 5–6%。
- 所以 **grouped 默认的理由是 CPU 余量和故障局部化，不是单码恢复率
  不够**。单码在 p≤20% 的恢复率是够的（M=64,d=64），代价是 3.6 倍的
  每比特 XOR 和整窗失败面。
- 若目标是 500 Mbit/s，单码 M=128,d=32 与 grouped M=4,d=4 的 goodput
  相同，但单码要 8.0 GB/s 标称（4.0 @1G 线速），grouped 只要 1.0
  （0.5 @1G 线速）。这个对比里 grouped 全面占优。

## 9. 局限

- **HND0 未实测。** 恢复率只取决于码（生产 `rlnc.c`）与丢包模型，与机器
  无关；XOR 判定用的是 `review/microbench.md` 的 HND0 单核 7.8–9.1 GB/s。
  本机没有跑 HND0 的 2 vCPU、256 条 TCP、软中断与解码。
- **L=W 是最坏形态。** 稳态 L>>W 时每个包落在两个完整窗口里，后半窗
  只有 M 行的劣势消失；本文按任务要求只测 L=W。hnd0 的 L=3W 探针
  （`review/hnd0-sim.md` §7）显示 d<W 时结论同型。
- **只测 iid 丢包。** 突发丢包（Gilbert-Elliott）会让单个窗口的丢失
  更集中；单码没有跨组修复，对突发比 grouped 更敏感。本文没有测。
- **整窗口径。** 恢复 = 整窗逐字节一致；没有 NACK/重传、没有部分交付、
  没有延迟与重排。实际可用性取决于恢复失败后的修复策略。
- **模型是近似。** §1.2 的闭式解忽略列间秩相关；60 点平均偏差 1.7e-4，
  最大 6.8e-3。判定用实测，不用模型。
- **xor_gbs 是公式，不是实测。** 纯编码实测执行 0.756 的标称项
  （公式的 0.375）；解码另做一遍系数与消元，p=20% 时约为编码的
  1.3–1.5 倍（d=32/64 的可行点）。公式用 q=2 作为编+解码预算，判定因此偏保守；本机探针
  不是 HND0 基准。
- **矩阵止于 p=20%。** p>20% 的阈值是模型外推，没有实测。
- **mem 列是解码工作区**（S=8192），不含 data/parity 缓冲；整窗合计
  5.01–6.01 MiB，见 §0 第 9 条。

## 10. 复现

```
cd review/fec-prototype
cc -O2 -std=c99 -Wall -Wextra -Werror -D_POSIX_C_SOURCE=200809L \
   -pthread sim_single.c rlnc.c -o sim_single
./sim_single 20000 > ../single-sim.csv
```

CSV 列：`M,N,W,d,p,trials,recovery,ci99,xor_gbs,app_mbit,mem_bytes`。
60 行，每行 20000 trial，共 1.2M 次。运行是确定性的：同一命令复现同一组
数字。程序参数 `[trials] [start] [count]` 只用于标定子集。
