# `retx_ppm` 的 96k 是什么，能不能降到 50k

只读分析，基于 `benches/results/20261105T112245-throughput.csv` 与
`-carriers.csv`。不构建、不跑 QEMU、不改源码。

---

## 0. 结论

1. 96,095 ppm 的**分母里 45% 是 FBK**。用数据帧做分母，真实数据重传率是
   **19.1%**（1,958 / 10,240），不是 9.6%。
2. 这个 19.1% 与线上重复载荷的占比 **15.9%** 自洽：整段传输 `wire/app` 是
   **1.2066**，不是 CSV 里那个 **1.0005**——后者是 2 s 采样窗口内的比值。
3. 所以 96k **既不是纯口径虚高，也不是纯行为问题**：口径把 19% 压成 9.6%，
   而 9.6% 仍然高于 5%（50k）。
4. 只改口径**不可能**诚实地降到 <50k：数据帧口径下 50k 只允许 512 份副本，
   现在有约 1,958 份。
5. 要真降到 50k，必须让副本数量减半到四分之一；最可能的主因是慢速路径
   （`tcp_done` + uack 未覆盖 + 2×RTO），而不是洞帧分支。这一点必须先用
   三个按来源的计数器证实，再动行为。

---

## 1. 96k 的构成

| 量 | 值 | 来源 |
|---|---|---|
| `frames`（Σ`tx_frames`） | 22,467 | CSV |
| `fbk_tx`（会话 FBK 数） | 10,171（**45.3%**） | CSV |
| 唯一 DATA 帧（80 MiB / 8192） | 10,240 | 计算 |
| 其余控制帧（HELLO/OPEN/FIN） | ~100 | — |
| 重传副本（写出，聚合） | **~1,958** | Σ`ppm_i·frames_i` |
| 聚合 ppm（逐载体求和） | 87,134 | 计算 |
| CSV 报告的 ppm（最差路径） | 96,095 | `peer_retx_max` |
| 数据帧口径的重传率 | **19.1%** | 1,958 / 10,240 |
| 副本载荷 | 16.1 MB | 1,958 × 8,224 |
| 线上总字节 | 101.2 MB | CSV |
| 副本占线上 | **15.9%** | — |
| FBK 占线上 | 1.05% | 10,171 × ~104 B |
| 整段 `wire/app` | **1.2066** | 101.2 / 83.9 |
| 窗口 `wire/app`（CSV 列） | 1.0005 | 2 s 采样窗口 |

三条独立的账对得上：`frames = 唯一数据 + 副本 + FBK`
（10,240 + 1,958 + 10,171 ≈ 22,369，与 22,467 差 0.4%，是 FIN/OPEN 与
取整）；`wire = 数据记录 + 副本记录 + FBK`（85.0 + 16.1 + 1.06 ≈ 102.2 MB，
实测 101.2 MB）。所以这个分解是可靠的。

**分母的偏差方向**：FBK 把分母撑大 45%，于是 19.1% 被报成 9.6%。
如果把 FBK 也算进“控制帧不计入分母”，数字会**变大**，不是变小。
`retx_ppm` 从来不是“数据帧重传率”，它是“定时器副本 / 全部记录”。

**窗口的偏差方向**：CSV 的 `wire_per_app` 取的是 2 s 速率窗口，窗口里
副本恰好很少；整段的 1.2066 才是真实开销。验收写 `<1.1` 时用的如果是
窗口值，会高估实际质量。

---

## 2. 副本从哪来

代码里能写出副本的只有三处，且都没有按来源计数：

| 来源 | 触发条件 | 在干净 bench 里应该有多频繁 |
|---|---|---|
| 洞帧分支 | `r->seq == tx_ack` 且（`last_ack_ns==0` 或 uack 停滞 ≥2×RTO），再受 RTO 节流 | 解析前沿一直在推进，uack 不该停 2×RTO；只应在 bootstrap 的极短窗口出现 |
| 慢速路径 | 所有副本 `tcp_done` 且 uack 未覆盖，持续 2×RTO | **最可能的来源**：帧被 TCP 快速确认，但 per-path uack 要等 FBK（4 条路径分摊 100/s → 每路径 ~25/s，即 40 ms 一次）；若某帧的 uack 因 FBK 排队而晚到 2×RTO（~180 ms），它就会被算作“TCP 已交付但 uack 未覆盖” |
| 路径死亡 `retx_now` | `carrier_lost` | `lost=0`，本 run 为 0 |

观测到的是 **17.5 份/秒**（1,958 / 111.7 s）。这个量级与“少数在飞帧的 uack
晚到”一致，与“每帧每 RTO 重发”不一致（后者会是每秒数百份）。

**结论（推断，需计数证实）**：主因是慢速路径在无丢包链路上对“uack 迟到”
的误判；洞帧分支只贡献 bootstrap 的一小段。

## 3. 能不能降到 50k

### 3.1 只改口径

| 口径 | 当前值 | 50k 的含义 | 能否达标 |
|---|---|---|---|
| 现状：副本 / 全部记录 | 9.6% | 1,124 份副本 | 需要减半 |
| 数据帧分母：副本 / 数据帧 | 19.1% | 512 份副本 | 需要减到四分之一 |
| 载荷比：副本字节 / 应用字节 | 19.2% | — | 需要减到四分之一 |
| 线上比：副本字节 / 线上字节 | 15.9% | — | 需要减到三分之一 |

**只改口径不可能达标**，因为每一种诚实口径下当前值都在 16%–19%。
口径修复是必要的（让数字可信），但不是充分条件。

### 3.2 行为收紧

| 方案 | 预期效果 | 对 J/K 3/3 的风险 |
|---|---|---|
| 慢速路径宽限 2×RTO → 3×RTO | 副本数约降到 2/3（~1,300），数据口径 ~13%，仍 >5% | 中：J/K 的修复依赖这条路径；3×RTO 只是更慢，理论上仍会触发，但 5 s 预算里余量变小 |
| 慢速路径加条件“该帧所在路径的 uack 也停过 2×RTO” | 干净链路几乎不触发（uack 在动），副本可能掉到接近 0 | **高**：K 的双条件死区正是“一条路径在动、另一条在黑洞”，这个条件会把 K 的修复关掉 |
| 洞帧阈值 2×RTO → 3×RTO | 只影响 bootstrap 后的洞帧，量很小 | 低到中 |
| 降低 uack 延迟（FBK 走 spare，bench 用 m=1） | 从根上消除“uack 迟到 2×RTO” | 低；但 bench 是 m=0，且这是配置而非代码 |

### 3.3 建议的顺序

1. **先加三个按来源的计数器**（`retx_hole`、`retx_slow`、`retx_pathloss`），
   一行一个，跑一次 n=4。没有这个分解，任何行为收紧都是猜。
2. **同时修口径**：`retx_ppm` 改用数据帧分母，另报一个 `dup_bytes_ppm`
   （副本载荷 / 应用字节）。验收里的 `<50k` 必须写清是哪个口径。
3. 如果计数证实主因是慢速路径：先试 3×RTO（低风险），再考虑“uack 停滞”
   条件（高风险，会伤 K）。
4. 如果主因是 uack 延迟：把 bench 也改成 m=1，让 FBK 走 spare，再测。
   这是配置改动，不动数据面。

---

## 4. 明确不该做的

- 不要把 FBK 从分母里删掉就宣布达标：那会让数字从 9.6% 涨到 19.1%。
- 不要用窗口 `wire_per_app`（1.0005）代替整段比值（1.2066）来验收。
- 不要在没加计数器之前调 2×RTO 或洞帧阈值：J/K 的 3/3 是这轮最脆的资产。
