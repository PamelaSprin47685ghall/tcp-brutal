## 1. 变更清单（v0.3.1 → a275dea）

### fix（5）

- **78d5a90** `fix: restore the carrier up count after a long run`
  - 每流 announce 标记只存 4 bit 的 carrier generation，替换载波
    `gen=292` 与死载波 `gen=4` 低 4 位相同，OPEN 被跳过，槽位永久
    `up=0`；载波丢失与 `join()` 安装新 generation 时清该标记。
  - HELLO 时排队的 OPEN 若遇控制队列满则无人重试；50 ms session poll
    现在对“HELLO 已写、up 仍为 0”的已连接载波重发 OPEN，计入
    `up_rescued`。
  - `tbt_session_retire()` 的 RETIRE body 带 peer generation，far 却拿
    自己的 `carrier->gen` 比较；两侧计数器会随单边拨号漂移，可能漏杀
    或误杀。改为比较 `peer_gen`。
  - c3 新增 `replacing=`、`empty=`，不变量
    `up + replacing + empty == n`；`up_rescued=` 也在 c3。
- **2f074e5** `fix: do not NACK a block while its decode settle window is open`
  - 50 ms decode settle window 与 NACK scan 在首连竞争：scan 请求
    frontier 缺口，far 重放，每次重放又重置 settle window。fix45 实测
    一次连接 482 个 NACK、27,465 个重放 share、226 MB，far
    NACK→wire 286.7 s。
  - 仅当块是 block codec、有 parity、`decode_tries == 0` 且仍在
    `decode_next_ns` 内时跳过该组。无 parity 的块不跳过；失败后的
    backoff 不抑制 repair。
  - `host/test_fec_rx` 钉住首次 settle 边界与失败后路径。
- **859ddd4** `fix: isolate the FEC data plane across a stream switch`
  - fix47 稳态连接收到 HTTP/0.9：第二条流读到第一条流的 body。near
    丢弃了 11,179 条 old-sid 记录，但 `far_sid` 先被清空、session
    barrier 被跳过，data plane 保留了旧投递状态；far 的旧 target 仍在
    向共享 TX/replay ring 喂数据。
  - near：新 sid 的 DATA/PARITY 到达且旧流已消失时，在 data plane
    重置 RX cursor 与 block；新流已 adopt 则中止重置。
  - near 投递：block 记录放置它的记录所属 sid，不再读会变化的
    `far_sid`；`tbt_fec_super_ready_locked()` 与投递 walk 拒绝非当前
    流的 block。
  - far TX：只有当前流可向共享 ring 追加；旧 target 的迟到读取被消费
    丢弃；过期 pending switch 被清除。
  - far TX switch：杀掉旧流（shutdown target）并重置 replay ring。
  - `host/test_fec_rx` 覆盖跳过 barrier、TX ring sid gate、stale switch、
    block/stream sid 匹配。
- **7751dc9** `fix: flush the whole FEC TX ring on a stream switch`
  - fix48 的稳态连接仍把旧 body 打上新 sid。切换用新流首次 submit 的
    offset 作丢弃边界；旧 target 的末次 submit 可越过该边界，随后被
    packetizer 打上新 sid，replay ring 又把它存回，near 的 NACK 继续
    重放旧 body。
  - 新流首次 submit 在 packetizer 仍持有旧 block 时被拒绝（返回 0、
    置 `tx_paused`、arm TX work）；switch work 清空整个 ring、杀旧流、
    重置 replay ring、重排 read work。
  - `switch_sid` 贯穿整个清理；`cur_block_sid` 最后发布，之后才清
    gate，submit 无法插入 flush 与新 owner 之间。
  - 无条件丢弃 `[tail, head)`；释放所有 replay 记录（含 sid-0 与
    raced 记录）。旧流的迟到 submit 在 gate 期间被丢弃。
  - 每次 submit 只取一次 `far_sid` 快照；清 stale switch 时恢复被拒流
    的 `tx_paused` 并重排 read。
  - 空块也关闭并推进，避免新流与旧 marker 的 block id 冲突。
  - near 流重置发布 `nack->valid=false`，避免切换后重发旧块 NACK。
  - 删除不再使用的 `switch_to` 字段。
- **a275dea** `fix: switch the TX ring from the packetizer, not only the submit path`
  - fix51 仍复现旧 body：packetizer 在新流首次 submit 之前运行，此时
    `cur_block_sid` 与 `switch_sid` 均为 0，切换条件未命中；它用旧
    ring 字节构建新 sid block，replay ring 又将其存下。
  - packetizer 也触发切换：末次 submit 来自不同流（含尚未建 block）
    时清空整个 ring；`switch_sid` 在 flush 前置位并贯穿清理。
  - 无 block 情况也拒绝新流首次 submit，关闭“packetizer 清掉 submit
    刚接受的字节”与“stale packetizer 让 `old_sid` 指向新流并杀掉它”
    的竞态。
  - 旧流即使从未建 block 也杀掉（`last_submit_sid`），阻止其 target
    继续喂 ring。
  - 发送时校验每条排队记录的 sid：data/replay 必须等于当前
    `far_sid`，sid 0 的 session control 记录保留；raced 记录在到达
    carrier 前丢弃。
  - `host/test_fec_rx` 钉住 packetizer 切换触发、无 block 拒绝、发送时
    sid gate。

### feat（含 perf，1）

- **78db715** `perf: decode FEC blocks once, at the end of their share burst`
  - 下行在一收到 parity share 时就认领解码，RX pass 在首次投递前最多
    解码 8 个 slot；HND0 上 1 MiB block 耗时 47.8 ms，每个投递 block
    平均解码 7.7 次，单个 `w_fec_rx` worker 用 0.96 核换 2.86 MB/s。
    上行 GF(16) 同样在多数 share 缺失时先解码；q-ary peeling 在 70%
    擦除时比 2% 慢约 3 倍。
  - 用安静窗口门控 block codec 解码：每个新 share 把
    `decode_next_ns` 推后 50 ms，burst 末尾合并为一次解码；失败
    backoff 50..400 ms；新 share 重置窗口；重复 share 不改变 block
    状态也不推迟解码。只解码投递 frontier，每轮解码后让出 RX body。
  - 64×8 逐位 gather/scatter 改为 8×8 SWAR transpose（双向同一变换，
    对合）。host -O2、1 MiB block：encode 135 → 528 MB/s；单 share
    擦除 decode 112 → 356 MB/s；0.5% share 丢失时 block-end decode
    3.8 ms（原 8.9 ms）。GF(16) uplink codec 不变。
  - `host/test_fec_sclc` 用 codeword 3 的单 bit 钉住 transpose 的
    codeword 轴。

## 3. 发布门清单

所有门必须在**同一个 tag-exact 树**上、**一次 `--run`** 内完成；失败
不重试、不降级、不拼接多次部分运行。证据目录必须完整。

- tag 必须指向 release commit；`EXPECT_TAG_COMMIT` 不得留空。
- 两端 ssh、锁、磁盘、端口 9001/9000 空闲、无残留 `tbtun` 模块、
  dkms 3.2.2、`dkms status` 为空、`/usr/src/tbtun-*` 与
  `updates/dkms/tbtun.ko*` 不存在。

- 先在 tag 树上跑 `make check`、`make host-test-san`、
  `bash review/lint.sh`，记录 0 failures。

### G1 tag-exact 构建与 identity

### G2 1 GiB 单流

形状：256 carriers、`mode=sc-ldpc`、`adaptive=off`、单流，超时上限
7200 s。

必须同时满足：

- 进程 rc=0，HTTP 200，字节数 `1,073,741,824`，两端 sha256 相等。
- 两端 c3 `up=256`（见 G4）。
- 以下窗口 delta 全为 0：`fec_outq_drop`、`fec_init_bad`、
  `fec_reset_hole`、`fec_epoch_conflict`、`fec_reset_tcp_failed`、
  `holes_unrecoverable`、`fec_deliver_bad`、`fec_replay_miss_enospc`。
- `fec_replay_queue_high < 5,242,880` B。
- `fec_replay_miss_never_stored <= 256`。
- `fec_short_parity_saved > 0`；`fec_nack_pad_skip = 0`。
- near `fec_ack_tx > 0`、far `fec_ack_rx > 0`。
- 内核窗口无 BUG/Oops/WARNING；`tbt_car_rx_work` hog 只作信息记录，
  但必须写进证据。
- `fec_outq_high_wait` 只作信息记录，不作为失败。

### G3 DKMS 七步

- 主机 `.82`，dkms `3.2.2`（dpkg `3.2.2-1ubuntu1`）。
- 七步：install、load、config read-back、rmmod、modprobe、read-back、

- `judge-dkms-log.sh <log>` 输出 `DKMS_JUDGE PASS`；无
  `DKMS_STEP ... rc=[1-9]`、无 `DKMS_CHECK ... FAIL`、无
  `DKMS_ROLLBACK`、`DKMS_RESULT PASS`。
- 结束后 `dkms status` 为空，`/usr/src/tbtun-*` 与
  `updates/dkms/tbtun.ko*` 清理干净。

### G4 watchdog

- `.82` 执行 `review/wan-experiment/arm64/netwatch-82/install-82.sh
  --arm`；先 `--dry-run` 只跑只读 selftest（selftest 不 open 设备）。
- PASS 证据：`systemctl is-active tbtun-netwatch`；MainPID 持有
  `/dev/watchdog0`；`/var/log/tbtun-watchdog.log` 有 `first feed ok`。
- 风险固定记录：驱动广告 MAGICCLOSE（options `0x8180`），close 不带
  magic `V` 不会停表；停 unit 即进入 44 s 倒计时，唯一受支持的退场
  是重启。scope audit 里“MAGICCLOSE=0”的措辞应在 gate 文档中改正。
- `REQUIRE_FEEDER=0` 的豁免只能记为 SKIP，永远不能记为 PASS。

### G5 up=256

- 1 GiB 结束两端 c3 `up=256`；稳态采样器全程 `up=256`。
- 诊断用新不变量 `up + replacing + empty == n`；替换窗口应表现为
  `up` 下降、`replacing`/`empty` 上升后回到 256，而不是泄漏。
- 记录 `up_rescued`；它非零说明 OPEN 重发路径生效，不单独判失败。
- 若无法达到 256：必须给出一条带数字的可用性规则（例如“全程
  `up >= 252` 且 byte-exact”），在 gate 中显式判定；不能像 0.3.1
  那样由脚本隐式 FAIL 后仍称发布。

### G6 NACK→wire

- 判据使用**窗口 delta** 的 `fec_nack_lat_ns`，不是 session 累计和：
  1 GiB `< 600 s`；稳态 60 s `< 180 s`。
- 同时记录 `fec_nack_lat_max_ns` 与 `fec_nack_repair_max_ns` 作为尾部

- `fec_nack_tx/rx/retx/drop` 记录绝对值与 delta；`drop` 不得增长。
- 0.3.1 的“502.20 s < 600 s”是累计和误判，不能沿用。

## 4. 回滚步骤

### 4.1 代码与 tag

- 发布前失败：不创建 tag；修复后重新走 G0–G7。不得用
  `git reset --hard` 改写已有历史。
- tag 已创建但未 push：`git tag -d v0.3.2`。
- tag 已 push 且发现阻断：**不移动已发布 tag**；发布 0.3.3，或在
  release notes 标注撤回。删除远端 tag 需单独授权。

### 4.2 现场模块

1. 两端写 `del 1` 到 `/proc/net/tbtun/config`，再 `rmmod tbtun`；
   确认 `lsmod | grep tbtun` 为空。
2. 装载上一版 v0.3.1 的 ko（保留的构建产物或 DKMS 0.3.1），确认
   `/sys/module/tbtun/version` 为 `0.3.1`。
3. 恢复原 tunnel/config 并重连；检查 c3 `up` 与 c9/c10/c11 无新增
   错误。
4. 若 `rmmod` 卡住：0.3.0 起 session drain 有 10 s 上限并会报告泄漏；
   收集 dmesg 与 `/proc/net/tbtun/stats` 后再决定，不强杀。

### 4.3 DKMS

- 优先 `scripts/install_dkms.sh --uninstall`（按其 usage 确认参数）。
- 手工兜底：`dkms remove tbtun/0.3.2 --all`；删除
  `/usr/src/tbtun-0.3.2`、`/lib/modules/<krel>/updates/dkms/tbtun.ko*`；
  `depmod -a`；确认 `dkms status` 为空。
- 重新安装 0.3.1 的 DKMS 条目并验证 `modprobe tbtun`。

### 4.4 watchdog（顺序不可颠倒）

- 只停止 feeder 等于启动 44 s 倒计时，不是关闭开关。
- 本 boot 继续受保护、下 boot 不武装：
  `rollback-82.sh --next-boot-only`。
- 彻底退场：`rollback-82.sh now`（disable、sync、reboot）；这是唯一
  受支持的退出方式。
- 回滚前先 `rollback-82.sh --status` 记录 holder、unit、uptime 与预算。
- 若修改过 cmdline（`nowayout-82.sh --prepare`），用
  `nowayout-82.sh --rollback` 恢复最新 `.bak-*`，并保留串口控制台。

### 4.5 版本号

- 把 `tbtun/tbt_uapi.h` 的 `0/3/2` 改回 `0/3/1`，同步 README、
  README.zh、DESIGN 三处；`make dkms.conf` 重新生成；重建并重装。
- 若已发布 0.3.2，不回退版本号；用 0.3.3 修正。
