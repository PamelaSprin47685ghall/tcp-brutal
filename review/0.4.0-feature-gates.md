# 0.4.0 特性门

基线 `v0.4.0` (`f8fab7b`)。测试对：near `root@192.168.123.85` /
`192.168.123.85`，far `root@45.11.1.62`。三个特性门都是真机验收；
脚本不构建、不加载模块、不重启对端服务。

## 共同前置

- 两端已部署同一 0.4.0 构建，root SSH 可达，`/proc/net/tbtun` 存在。
- 验收会改写隧道 1（portmap 为 1..6）和端口窗口；只在测试对运行。
- 证据目录默认在 `benches/results/` 或 `$EVIDENCE_ROOT` 下，每次运行新建。

## 门 1：多流 FEC v7

命令（模块参数必须两端一致，且只能通过重新加载生效）：

```sh
# 两端：重新加载模块，参数 16
insmod tbtun.ko fec_groups_per_flow=16
scripts/qa/multistream-accept.sh --status
scripts/qa/multistream-accept.sh --setup --run --bytes 1073741824 \
    --evidence /root/tbtun-ms-ev
# 参数 0 的拒绝路径：两端重新加载 fec_groups_per_flow=0 后
scripts/qa/multistream-accept.sh --param0 --evidence /root/tbtun-ms-ev-p0
# 恢复 --setup 保存的配置
scripts/qa/multistream-accept.sh --cleanup --setup --evidence /root/tbtun-ms-ev
```

前置：

- 隧道配置 `fec=on mode=grouped carriers=256`，`crypto=off`；
  脚本默认写入该配置，`--setup` 会覆盖两端现有配置。
- far 侧有 `python3`，near 侧有 `curl`；远端起 `multistream-target.py`，
  目标端口默认 5210，两条流分别请求 `/stream/a`、`/stream/b`。
- near 两个固定本地源端口 41001/41002 未被占用。

判据（脚本内 `qa_check`，全部通过才 `RESULT PASS`）：

- 两端 `fec_groups_per_flow` 等于期望值；`fec=on`、`mode=grouped`、
  `carriers=256`；c3 `up=256`。
- 两条流同时活跃、sid 不同、`fec_drop_sid` 不增长；两个 body 的 sha256
  与 far 侧一致且互不相同；字节数精确等于 `--bytes`；far 记录两条路径且
  无 `REJECT`。
- `--param0`：第二条流被拒（curl 非 0），`fec_stream_refused` 增长，
  仍只有一条流。

已知限制：

- v7 在 `mode=sc-ldpc` 下只允许一条 flow（`tbt_fec_flow_create` 返回
  `-EOPNOTSUPP`），多流门必须用 RLNC `mode=grouped`；SC-LDPC 单流是设计
  边界，不是本门失败。
- 多流配置使用 `crypto=off`；本门不验证加密路径。
- 脚本不重载模块，参数切换要人工重载；`--setup` 会中断该对上的其他隧道。
- 没有 `--dry-run`，预检用 `--status`。
- 0.4.4 起 `--param0` 改验动态分配默认（第二条流被接纳）；要重跑本门，
  请用 0.4.0 树里的同名脚本。

## 门 2：SC-LDPC 自适应速率

命令：

```sh
benches/adaptive/sclc-0.4.0.sh --near root@192.168.123.85 \
    --far root@45.11.1.62 --near-ip 192.168.123.85 --far-ip 45.11.1.62 \
    --source /root/accept-1g/accept-2g.bin --quick --tag smoke
# 完整矩阵：--full；只预演：--dry-run --quick
```

前置：

- 两端 0.4.0 构建，`mode=sc-ldpc`，c13 可读；far 模块以
  `debug_loss=1` 加载（`drop_ppm` 注入）。
- far 源文件存在（建议 2 GiB，60 s 窗口不被提前下完）；far 原始发送端
  监听 `127.0.0.1:5210`（`review/wan-experiment/arm64/prod-1g/far-serve.sh
  --start`）。
- near 经 `--dev`（默认 eth0）可达 far；共享 harness 会加 pref-100 ip rule。
- 只支持 `carriers=256`；隧道 1 会被改写。

判据（`verdict.txt` 的 S1..S7，`S_RESULT: PASS` 为门通过）：

- S1：每轮 sha256、字节数、lost/stall/holes/reset、up=256 干净。
- S2：自适应轮 p_est 误差 ≤1.5 pp；0 损轮 p_est ≤0.5%。
- S3：最终上行速率落在阶梯上；下行配置 128/128，上行 8/24 起始。
- S4：每轮切换 ≤3 次、反向 ≤1 次，c13 采样存在。
- S5：六档上行速率 {25,30,40,50,60,70} 全部出现（自定义 `--loss` 时 SKIP）。
- S6：fixed/default 保持 8/24 rate25、零切换、`adaptive=off`。
- S7：记录 adaptive-vs-fixed 的 app/wire 对比，不作通过条件。

已知限制：

- SC-LDPC 当前只支持单流；本门不叠加多流。
- 下行 TX 是固定 binary codec（1x256、L8、rate 0.50），控制器不会切换
  下行速率；脚本只断言下行配置并记录 far c13，不要求下行变速。
- far c13 是下行 RX 视图，可能与 far TX tick 混合；上行速率以 near c13
  为准。
- 依赖 `debug_loss=1` 和 far 源服务；两者缺失时无法完成注入/传输。

## 门 3：per-tunnel portblock

命令：

```sh
scripts/qa/portmap-accept.sh --near root@192.168.123.85 \
    --far root@45.11.1.62
# 可选：--strict-reserved --out /path --carriers 4 --keep
```

前置：

- 两端 0.4.0 模块已加载；root SSH；`/proc/net/tbtun/{config,ports,peers,stats}`
  可读。
- 只在测试对运行：脚本替换隧道 1..6 和全局端口块，退出时恢复保存值
  （`--keep` 保留测试配置）。
- 不需要应用流量；far target 是 `127.0.0.1:1`，不会拨号。
- 默认窗口：near 30000-30511 / 30600-30799，global 40000-40031 /
  40100-40131，far 31000-31015；可用环境变量覆盖。

判据（`PORTMAP_RESULT PASS`，退出码 0）：

1. 两个 near 隧道只从各自窗口取源端口，无重复 sport、无重复
   `(sport, peer)` 五元组。
2. 窗口重叠的第三个 near 隧道得到 `port_exhaust` 且保持空，不抢活端口。
3. `portblock=0-0` 回退到全局 `/proc/net/tbtun/ports` 窗口。
4. 写 `/ports` 只影响新分配，活 carrier 保留端口；写回旧窗口仍跳过活位。
5. far 只记录 `portblock=`，不分配源端口；far `port_exhaust`/
   `port_alloc_fail` 为 0，peers 视图显示 near 窗口内的源端口。

已知限制：

- 不发送应用流量，只验证 carrier 端口分配与冲突语义。
- 不构建、不加载/卸载模块；两端必须已运行 0.4.0。
- 不改 `net.ipv4.ip_local_reserved_ports`；未保留窗口只告警，
  `--strict-reserved` 才转为失败。
- 单次执行；默认恢复配置，`/ports` 的 `default` 视图会恢复为同块的显式写。
- 没有 `--dry-run`；无硬件时无法本地演练。

问题记录：

- `multistream-accept.sh --help` 走 `usage()` 的 `exit 2`；惯例应为 0。
  不影响运行，但会把帮助当用法错误。
- 只有 `sclc-0.4.0.sh` 支持 `--dry-run`；另两个脚本传该参数会以
  “unknown option/argument” 退出 2。门 1/3 只能靠 `--status` 或人工预检。
- `sclc-0.4.0.sh` 的 shebang 是 `#!/bin/sh`；本次只做 `bash -n` 语法检查，
  未在 dash 下执行。
