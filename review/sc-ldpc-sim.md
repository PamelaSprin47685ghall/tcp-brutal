# SC-LDPC / SC-IRA 原型：构造修正、BEC 曲线与 CPU 结论

日期 2026-11-06。代码：`review/fec-prototype/sc_ldpc/`
（`sc_ldpc.c`、`sc_ldpc.h`、`sc_ldpc_bench.c`）。
构建：`review/fec-prototype/sc_ldpc/build.sh`，一行
`cc -O3 -std=c99 -Wall -Wextra -Werror sc_ldpc.c sc_ldpc_bench.c -lm -o sc_ldpc_bench`。
数据：`review/sc-ldpc-sim.csv`（66 个对称点：54 个 rate 0.50/0.60/0.70 点
+ 12 个低速率点，每点 2000 trial）与小规模点（正文表 2、表 3）。

## 0. 结论

1. **原来的 symmetric 0.000 不是解码器少写了一层 BP，而是图的尾部有 2 变量
   stopping set。** 原始 causal 终止删掉了尾部 4 个 check supernode；最后一个
   variable block 的 payload 和 parity 都只连到同一个 check。两者同时擦除时，
   该 check 的两个未知数永远解不出。p=0.30 时每对发生概率 0.09，m 个 copy 中
   至少一对失败的概率趋近 1，所以任何 L 的全恢复率都是 0。逐波 peeling 的
   实现本身是对的：初始 ucnt==1 入队、解出变量后递减邻接 check 的 ucnt、
   降到 1 再入队，直到队列空；它等价于 BEC 上的迭代 BP，不是一次性 degree-1。
2. **修正后的构造是 SC-IRA**：payload 度 5 的环形窗口（check 下标模
   `n_base`），parity 度 2 的累加器（check a 拥有 parity a，并送入 check a+1），
   check 度 6–7。rate 0.50 时 `n_chk = L*m`；rate 0.60/0.70 时把 `n_base`
   缩到 `round(L*(1-R)/R)` 个 check supernode。编码是一次正序扫描，parity
   子矩阵为下双对角，永不奇异。
3. **小规模全部 bit-exact。** N=16/32、L=2/4、rate 0.50、p=0.01/0.10：
   `payload_check` 的 4096/2048 个码字 bit_errors=0；p=0.10 的 2000 trial
   全恢复率 0.9995–1.000。矩阵统计见表 2。
4. **任务给的 (rate, p) 组合正好是 BEC 容量点**：0.70/0.30、0.60/0.40、
   0.50/0.50 都满足 `rate = 1-p`。有限长度码在容量点不可能达到 0.999；
   实测 0.000–0.9985（表 4）。有余量的点可以：rate 0.50 p=0.30 是
   0.9990–1.0000，rate 0.60 p=0.30 是 0.9395–1.0000，rate 0.70 p=0.20
   是 0.9115–1.0000。
5. **吞吐：-O3 单线程，编码 30–43 MB/s，解码 8–36 MB/s**（payload 口径；
   依赖 rate 与 p，p 越高 peeling 越早停、数字越好看但没有意义；低速率点的
   解码是 2–7 MB/s，见第 5 节）。有效工作点
   rate 0.50 p=0.30：编码 31–33 MB/s、解码 11–12 MB/s。1 Gbit/s 应用需要
   125 MB/s，单码字差 4 倍（编码）和 10 倍（解码）。HND0 快照的
   5.1/1.6 MB/s 比本机低 6–8 倍，但即使按本机也达不到 125。
6. **profile：解码占 84% CPU**（gprof，`sc_decode` 4.35 s / 5.18 s；
   `make_mask` 10%，`sc_encode` 4%）。热点是 peeling 的随机间接寻址：
   每解出一个变量要更新 5–7 个 check 的 `cx`（xorv/ucnt 合并），每边约 3 个周期，
   受 L2/L3 延迟限制，不是 XOR 吞吐。
7. **Verdict 分两层。** 对 1 Gbit/s（125 MB/s）目标，SC-LDPC 不可行：
   p=30/40/50 对 rate 0.70/0.60/0.50 是容量极限，0.999 信息论不可能；
   单码字吞吐差 10 倍。**但对 33.72 Mbit/s（4.2 MB/s）目标，存在可行的
   低速率工作点：rate 0.40、p=0.40、block 512、L=8/16，recovery
   0.9995–1.0000，解码 6.9–7.2 MB/s，是目标的 1.6–1.7 倍，单核即可。**
   rate 0.35/0.30 在 p=0.50 下 recovery 0.996–1.000，但解码 2.1–5.6 MB/s，
   只有部分配置过 5 MB/s。

## 1. 构造

### 1.1 npminh12 的规则

参考实现是 `npminh12/Spatially-coupled-LDPC`（commit 3d403f4，MIT，
Copyright (c) 2019 npminh12）。只取构造规则和 BEC 消息语义，没有复制 C++ 代码。
原文的图：

- protograph 是 regular (l,k)=(5,10)，q=k/l=2；
- coupling 位置 i∈[0,L) 放 q=2 个 variable 列，每列 m 个 copy；
  列 (r,i) 连到 check supernode i..i+4；
- lifting 对每条 (列, supernode) 边独立随机置换 m 个 copy，
  copy b 落到 supernode a 的 check 节点 `a*m+perm[b]`；
- 保留尾部 l−1=4 个 check supernode（native 终止），
  `M=(L+4)*m`，设计 rate `1-(L+4)/(2L)`。L=500 时约 0.496。

native 终止的 check 数比 parity 多 4m，码率不是精确 0.50，而且不能按
owned parity 做后向代入编码。原型保留 `SC_TERM_NATIVE` 仅作对照。

### 1.2 偏差与原因

1. **`SC_TERM_CAUSAL`（保留作对照，不用于结论）**：删掉尾部 4 个 check
   supernode，`M=L*m`，每个 check 拥有一个 parity，rate 精确 0.50。
   它的尾部 2 变量 stopping set 见第 0 节第 1 条；p=0.30 时全恢复率为 0。
2. **`SC_TERM_ACC`（生产构造）**：payload block i 的基准 check 是
   `base=floor(i*n_base/L)`，连 `(base..base+4) mod n_base`，度 5；
   parity block a 连 check a 和 a+1（a<n_base−1），度 2（最后一个度 1）。
   这打破尾部 stopping set，保持 rate 0.50，编码是一次正序扫描。
   `n_base=L` 时 rate=0.50；rate 0.60/0.70 时
   `n_base=round(L*(1-R)/R)`，check 数随之减少。
3. **rate<0.50 的额外 check**：`build_extra()` 保留在代码里，但本轮验收
   只跑 0.70/0.60/0.50，未使用。
4. **平行边**：L<5 或 n_base<5 时环形窗口会重复 check supernode。
   填充时对重复的 supernode 重新抽置换，保证同一 variable 不连同一 check
   节点两次。小规模 L=2/4 因此没有平行边，`payload_check` bit-exact。

### 1.3 编码与解码

编码：对 a=0..n_base−1 正序，`code[owned[a]] = XOR(check a 的其它变量)`。
check a 只依赖 parity 0..a−1（累加器链），所以一次扫描完成；extra check
在基础码之后计算。`sc_verify()` 检查全部方程。

解码：BEC peeling / 迭代 BP。初始化对每个变量做一次：已知变量把值 XOR 进
邻接 check 的 `xorv`，擦除变量把邻接 check 的 `ucnt` 加一。`ucnt==1` 的
check 入队。每波处理队列：取唯一未知变量，置为 `xorv`，再更新它的邻接
check（`xorv ^= x`，`ucnt--`），降到 1 的入队。重复到队列空。
`xorv` 和 `ucnt` 合并成一个 `uint16_t`（低字节值、高字节未知数），
每个 check 一次 cache line 访问。

## 2. 小规模矩阵检查

构建命令固定，`--dump` 打印 `sc_degrees()` 的直方图。
`vdeg d:c` 表示度 d 有 c 个变量节点，`cdeg` 同理。

表 2（block 16/32，L=2/4，rate 0.50，symmetric）

| block | L | n | data | par | chk | edges | vdeg | cdeg | rate |
|---|---|---|---|---|---|---|---|---|---|
| 16 | 2 | 32 | 16 | 16 | 16 | 104 | 1:8 2:8 5:16 | 6:8 7:8 | 0.500 |
| 16 | 4 | 64 | 32 | 32 | 32 | 216 | 1:8 2:24 5:32 | 6:8 7:24 | 0.500 |
| 32 | 2 | 64 | 32 | 32 | 32 | 208 | 1:16 2:16 5:32 | 6:16 7:16 | 0.500 |
| 32 | 4 | 128 | 64 | 64 | 64 | 432 | 1:16 2:48 5:64 | 6:16 7:48 | 0.500 |

解释：度 5 的是 payload（环形窗口 5 个 check）；度 2 的是普通 parity
（own check + 下一个 check）；度 1 的是最后一个 parity block（累加器在
check n_base−1 停止）。check 度 6 是“5 payload + 1 parity”，度 7 是
“5 payload + 2 parity”。终止是 `SC_TERM_ACC`，不是 npminh12 的
`L+4` check native 终止；表里的 `chk` 等于 `par`，所以 rate 精确 0.500。

### 3.2 容量分析

BEC 容量是 `1-p`。任务的三组点：

| rate 目标 | p | 1−p | 关系 |
|---|---|---|---|
| 0.70 | 0.30 | 0.70 | rate = 容量 |
| 0.60 | 0.40 | 0.60 | rate = 容量 |
| 0.50 | 0.50 | 0.50 | rate = 容量 |

在容量点，可靠通信要求码长趋于无穷；任何有限长度码的全恢复率都小于 1，
0.999 不可达。实测与这个判断一致。反过来，有余量的点可以：

| rate 目标 | p | 1−p | 余量 | 实测 recovery |
|---|---|---|---|---|
| 0.50 | 0.30 | 0.70 | 0.20 | 0.9990–1.0000 |
| 0.50 | 0.40 | 0.60 | 0.10 | 0.9945–0.9985 |
| 0.60 | 0.30 | 0.70 | 0.10 | 0.9395–1.0000 |
| 0.70 | 0.20 | 0.80 | 0.10 | 0.9115–1.0000 |

余量 0.10 时，L=8 的有限长度损失明显（0.91–0.98），L=16/32 接近 0.9995–1.0。
要稳定 0.999，余量应 ≥0.15–0.20。

## 4. 性能

### 4.1 测量方法

`measure_enc` 对固定 payload 重复 `sc_encode` 0.20 s，按 `n_data/8` 折算
payload MB/s；`measure_dec` 用 symmetric p 的固定 mask 重复 `sc_decode`。
`iter_mean` 是 peeling 波次数；`edge_visits_mean` 是初始化加各波的边访问数。
`latency_ms` 是 1 Gbit/s 下 L 个 8192 字节 payload 块的传输时延
（`L*8192*8/1e9*1000`），不是解码延迟。解码延迟可由
`(n_data/8)/dec_mbps` 估算：rate 0.50 block 256 L=8 约 10.4 µs/码字。

### 4.2 数字

- 编码：30–43 MB/s。rate 0.70 最快（图小、check 少），rate 0.50 约 31–33。
- 解码：有效工作点 rate 0.50 p=0.30 是 11–12 MB/s；rate 0.60 p=0.30
  是 11–15 MB/s；p=0.40 时 9–11 MB/s（波次更多）。
- 迭代：rate 0.50 p=0.30 约 7–8 波；p=0.40 约 16–18 波；rate 0.60
  p=0.30 约 12–15 波；rate 0.70 p=0.30 约 2–5 波（早停）。
- 内存：`sc_code` 59 KB（n=1408）到 654 KB（n=16384），包含 CSR 邻接、
  解码 scratch 和 owned 表。1G 应用不需要按速率放大。
- 编译：`-O3`，无 `-march=native`、无 SIMD、无线程。

### 4.3 profile

`gprof`（`-O3 -pg`，rate 0.50 block 512 L=32 p=0.30，20000 trial）：

```
83.98%  sc_decode
10.04%  make_mask
 4.25%  sc_encode
 1.74%  run_cfg
```

解码内部没有单一算术热点：时间花在 `cadj`/`vadj` 的随机间接寻址和
`cx[c2]` 的读-改-写。rate 0.50 block 512 L=32 p=0.30 每 trial 约 98k
次边访问、解码约 90 µs，折合 1.1 边/ns，即每边约 3 个周期（3 GHz），
接近 L2/L3 延迟而不是 ALU 极限。把 `xorv`/`ucnt` 合并成 `uint16_t`
（每 check 一次 cache line）带来约 10% 提升；`__builtin_prefetch`
没有稳定收益，已回退。

### 4.4 125 MB/s 是否可达

单码字、单线程：不可达。编码差 4 倍，解码差 10 倍。

可行路径只有两条：

1. **位并行批处理 64 个码字**。编码是纯 XOR、无分支，64 路位并行可以把
   32 MB/s 提到 >1 GB/s。解码难一些：BEC peeling 需要按位判断“某个 check
   在某一位上是否只剩一个未知变量”，要为每个 check 维护
   `unknown_mask`/`xor_mask`，并对每一位找唯一未知变量。标准做法是
   对 check 的每条边算 `unknown_mask & ~known_mask[v]` 再做唯一性归并，
   每波 O(deg²) 位操作。实现工作量明显大于当前原型，但理论吞吐是 64 倍。
2. **多线程**。每个码字独立，8 核约 8 倍，解码到 80–100 MB/s，仍不到 125；
   HND0 只有 2 vCPU（见 `review/hnd0-sim.md`），收益约 2 倍，更不够。
   多线程还会增加排队延迟，与 1G 小缓冲冲突。

所以即使不考虑恢复率，125 MB/s 也需要一次解码器重构，而不是调参。

**XOR 吞吐不是限制。** 编码每个 payload 字节约 7 次单比特 XOR
（`edges/n_data`），31 MB/s payload 对应约 220 MB/s 的 XOR 操作，
远低于 HND0 的 9.1 GB/s。解码的 XOR 更少，时间花在随机 load/store。
所以“XOR ≤9.1 GB/s”这一条不是否决项，否决来自恢复率与内存延迟。

图规模（`n / n_data / n_chk / edges`）：rate 0.40 的 block 512/L=16 是
10240/4096/6144/39424；rate 0.35 是 11703/4096/7607/47286；rate 0.30 是
13653/4096/9557/57767。`rate_actual` 与目标差 <0.01%（低速率点的 extra
check 是逐个 bit 追加的，不按 m 对齐）。

判断：

- **rate 0.40、p=0.40 成立，推荐为低速率工作点。** 四个配置的 recovery
  是 0.9985 / 1.0000 / 0.9995 / 1.0000。block 512 的两点都在 0.9995 以上；
  block 256/L=8 的 0.9985 距 0.999 只有约 0.2 个 99% 半宽（0.0028），
  可以按 0.999 量级使用。解码 6.9–7.4 MB/s，是 4.2 MB/s 目标的
  1.6–1.8 倍；编码 21.7–22.7 MB/s。单核、单码字即可，不需要位并行。
  block 512/L=8 延迟 0.524 ms；L=16 延迟 1.05 ms 但恢复更稳。
- **rate 0.35、p=0.50 接近但不稳。** recovery 0.9960–0.9985，全部低于
  0.999；解码 4.1–5.6 MB/s，只有 block 256 的两点过 5 MB/s。要 0.999
  需要更大 L、更多 extra check，或把 p 降到 0.45 左右。
- **rate 0.30、p=0.50 的恢复可以到 1.0（block 256/L=16），但解码
  2.1–4.6 MB/s，低于 5 MB/s。** 图更大（n=6827–13653，波次 11–12），
  单核余量不够；若产品只需要 4.2 MB/s，block 256/L=8 的 4.6 MB/s 也只是
  刚好，不建议作为首选。

**产品口径结论**：33.72 Mbit/s 用 rate 0.40 @ p=0.40 即可，单核解码
6.9–7.4 MB/s，余量 1.6–1.8 倍。p=0.50 需要 rate ≤0.35，此时单核解码
接近或低于 5 MB/s，需要多线程或位并行才有余量。

## 6. Verdict

**按 33.72 Mbit/s（4.2 MB/s）的产品目标，SC-LDPC 有可行工作点：
rate 0.40、p=0.40，block 512、L=8 或 16。** 1 Gbit/s 目标仍然不可行，
但那是另一个量级，不应据此否决低速率场景。

1. **低速率可行。** rate 0.40 @ p=0.40：recovery 0.9995–1.0000
   （block 512），解码 6.9–7.2 MB/s，是 4.2 MB/s 的 1.6–1.7 倍；编码
   21.7–22.7 MB/s；单核、单码字、内存 0.23–0.46 MB。选 block 512/L=8
   延迟 0.524 ms，或 L=16 延迟 1.05 ms 换更稳的恢复。
2. **p=0.50 不是免费余量。** rate 0.35 在 p=0.50 下 recovery
   0.996–0.9985，解码 4.1–5.6 MB/s；rate 0.30 可以到 1.0 但解码
   2.1–4.6 MB/s。如果产品必须 p=0.50，建议 rate 0.40 配更大 L（32/64）
   重测，或接受多线程；不要直接拿 0.35/0.30 的单核数字当余量。
3. **1G 不可行。** 125 MB/s 需要位并行（64 码字）或多线程（HND0 只有
   2 vCPU）；单码字编码 30–43 MB/s、解码 8–36 MB/s。且 p=30/40/50 对
   rate 0.70/0.60/0.50 是 BEC 容量点，0.999 信息论不可能。这两条只否定
   1G 场景。
4. **构造成立。** 修正后的 SC-IRA 在小规模 bit-exact，在有余量的点上
   0.999–1.0，编码一次扫描、parity 子矩阵下双对角、无 2 变量 stopping set。
   `--term causal` 和 `--term native` 保留为对照。
